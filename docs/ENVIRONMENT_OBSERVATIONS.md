# Practical environment observations

The original PE roadmap defines six environment-backed items in0.8.1. Their U/G/P status is separate from chat checkpoints and never blocks a tier gate. A learner's description alone is REPORTED_EXPOSURE unless relevant output is reviewed. Capture alone does not perform or certify that review. An optional native review workflow is now available as described below.

Open Inspect → Practical environment observations. Select one of the six source-defined items, describe your own actions, environment, what ran and what you observed, then optionally attach a finished saved code run or a supporting text/log/shared-code file up to256KiB. The full selected scope remains readable below the selector. Saving creates a pending-review observation packet. A connected native bridge advertising `review-environment` enables an explicit Review observation action in a live learner profile. Otherwise, use downloaded packets and the full game backup for external review.

A runner attachment includes the immutable captured code/revision, exact receipt/image/code hash, actual execution-event sequence and human-edit references. It must have a matching runner journal artifact and a reconstructable human-edited source revision. Merely storing a receipt-shaped object, NPC-only work, interrupted jobs or a different code snapshot cannot be attached. A later editor change does not replace the captured code. This is a fact about execution, not proof that the learner independently wrote tests, implemented a complete feature or met the whole ENV definition.

Learner-supplied files retain their decoded text, filename, text digest and explicit unreviewed provenance. They do not become trusted runner output. Report-only packets contain no claimed runtime observation. All packets retain the exact curriculum source/scope, capture time, original live/development profile and unassessed independence. History references support later review; full attributed edits and private tutor assistance remain in the complete game backup, so a packet alone does not establish independence.

Packets use a separate UUID namespace and allocate no S/A/EV IDs, visits, passes or reviews. Capturing a raw packet leaves ENV readiness and the complete merged roadmap unchanged. A raw observation cannot promote an ENV item, alter an academic checkpoint or satisfy a gate. The actual authoritative curriculum bytes are preserved.

Packets survive death, fresh runs, profile changes and JSON backups. Archived execution references keep their original run/encounter identities. The inspector can download each packet as JSON. Repeating an identical capture, including concurrent requests or after reload, returns the same packet rather than manufacturing duplicates. Each packet includes its own code/receipt or supplied output, so later source changes cannot silently rewrite it.

Persistence failure is explicit: the in-memory packet and its download remain available, the UI does not claim a successful local save, and retrying after storage recovers preserves the same ID. Export the packet or full run before leaving if saves fail.

Current verification: seven focused source/receipt/attribution/idempotency/archive/no-credit cases; actual Chromium text upload, inert rendering, narrow layout, running simulation, download and reload; actual Docker receipt attachment within the existing container workflow; and forced failure of both browser storage mechanisms followed by download/retry/reload. These are developer fixtures, not human ENV observations or certification. Browser/React environments, profiling, screen-reader observation, repository and AI-tool workflows still require actual appropriate practical work and review.


## Explicit practical review

Review observation sends the saved packet to the optional native `review-environment` operation. It sends the exact source item and scope, original capture profile, statement and supplied output/runner receipt. Runner-backed packets also include the original attributed workspace and tutor/group history through the execution cutoff, including private assistance relevant to the human review. Later code or tutor replies cannot replace that captured context. The native review occurs only on an explicit request, with at most one review in flight for this learner profile. A raw packet captured during development can later be reviewed under a live profile; its original provenance remains unchanged.

The reviewer distinguishes reported exposure (U), partial observation (G), and full source-scope observation (P). G/P require relevant supplied output references, an exact learner-work statement reference and coverage findings. P additionally requires the reviewer's full-scope judgment and no remaining coverage. A generic Python/Node run cannot establish browser rendering, profiling, screen-reader use, repository navigation or end-to-end testing. Text files remain learner-supplied evidence; they never become trusted runner receipts. Semantic judgment about relevance and learner ownership remains the native reviewer's responsibility. Partial packets do not automatically combine into P or downgrade a prior qualifying observation.

ENV P means observed learner work, not independent academic understanding. Reviews allocate no S/A/EV IDs, visits, checkpoint/transfer/integration passes, retention checks or tier changes. They use separate environment-review UUIDs and append-only practical evidence. The original raw packet remains immutable and still says pending-review; the review queue and separate evidence record hold its actual review outcome. Individual packets and the complete evidence backup remain downloadable. Detailed actions, output and attribution are in that backup; the merged roadmap contains bounded ENV status, review references and request/judgment digests rather than private logs or code.

Outages retain the exact normalized request ID, payload and digest for explicit retry. Reopening Inspect, time passing and reload never reroll or resubmit it. Reload marks pending requests interrupted. Canonical packet replacement, profile/source changes, missing original runner history, invalid output/ownership references and altered saved context prevent application. Readiness updates after completion even if Inspect was closed and reopened while awaiting the result. Browser storage failure preserves the in-memory review and downloadable evidence backup, reports the failed save, and allows normal saving/export after storage recovers.

Validated practical reviews project into the six original ENV rows and their separate dashboard count. ENV-only exports preserve protected curriculum bytes, academic ledgers/history and scheduler queues, update save anchors/migration metadata, and allocate no academic identifiers. Repeated unchanged downloads are byte-identical. Further actual reviews create a new revision with the exact complete prior export as parent. Exports containing academic attempts also include these practical receipts.

Verification adds eleven focused review/identity/source/ownership/attribution/retry/archive/export cases and two Chromium workflows covering explicit outage retry, inert native text, leaving/reopening Inspect during a held response, separate ENV P, complete Markdown download/reload, actual failure of both browser storage mechanisms, evidence backup and recovered saving. All272 engine/learning cases and24 Chromium workflows pass, including the existing real Docker execution workflows. Generated candidates and review judgments in these tests are synthetic; no actual learner has been ENV-certified and genuine native semantic quality/provider identity remain unverified.
