# ChatGPT handoff connector

This is a separate non-API ChatGPT connector for the game, adapted from generic transport/security code in the user's Infinite Canvas project. It does not verify or claim native ChatGPT Study Mode. The original native adapter remains available separately. No production credentials, job state or application generator were copied from the reference project; see `scripts/chatgpt-security/PROVENANCE.json`.

## Local setup

Run `npm ci` and `npm run dev`, then open http://127.0.0.1:5173. Settings → ChatGPT handoff controls release of study requests. It starts disabled on every relay launch. Development practice remains separate and earns no academic credit. Enable release explicitly, then select a live study profile to issue actual learning requests.

A local MCP client can run `npm run bridge:mcp` from this project. The stdio adapter reads the owner-only worker token written by the running relay; it exposes only get, read-part and submit tools. It provides no shell, filesystem, browser or code-execution tools. The game can run its separate restricted Docker workspace executor when explicitly requested by the player.

## Separate public connector

`npm run bridge:configure` provisions this game's distinct Cloudflare tunnel and subdomain under `lullascape.com`. It requires authorized Cloudflare access and installed `cloudflared`. It records intent before remote changes so interrupted setup retries the same resource. Private configuration and tunnel credentials stay in ignored `.local/`, with restricted permissions. It validates the pinned binary, exact tunnel UUID, credential file, Unix-socket ingress, catchall 404 and a freshly fetched official connector network list. Do not commit these runtime files or substitute another project's tunnel configuration. A global cloudflared update changes the pin and requires deliberate reconfiguration.

In game Settings, expand the connector controls and choose Start public connector. Verify connected/verified status. The displayed MCP URL is specific to this game's tunnel. In ChatGPT Plugins → Add → Add custom MCP server, use that URL, a separate name (zombie-escape-study-game), and OAuth. Review and approve creation yourself. Open its short pairing window in the game when ready to link; this does not enable study sharing. Enable release separately when ready to serve study requests. Use the local pairing code on the OAuth consent page. Close pairing afterwards. Create worker instructions locally and paste the scoped starter into the intended ChatGPT conversation with this connector selected. It supplies the current worker session, which is required on every tool call. Never paste another application's worker session.

A new worker session releases old claims and invalidates their session. Stop worker & sharing invalidates the current session, disables release and requeues its outstanding claims, including when sharing was already off; it preserves the OAuth link. Disconnect/revoke disables release. Stopping the public connector disables release and stops only its owned child process. The bridge now runs separately from Vite. Stopping or restarting `npm run dev`, a browser reload or a frontend update reuses the same bridge process, in-memory worker session, sharing choice and pending queue. `npm run bridge:start` starts or reuses that service; `npm run bridge:status` inspects it; `npm run bridge:stop` explicitly ends sharing, the worker and its owned tunnel. The private management endpoint requires an owner-only local control token, verifies project/instance identity and rejects browser-origin calls. Startup is serialized, and unrelated listeners are never replaced. A bridge-process shutdown/crash still ends the owned tunnel through its watchdog. Restarting that bridge itself leaves sharing and public tunneling off; the OAuth grant may remain saved, but a fresh local worker session is required. The persistent relay keeps diagnostics in the ignored, owner-only `.local/bridge-service/` directory. Startup can reclaim an owned abandoned Unix socket only after a connection probe returns ECONNREFUSED and its identity is unchanged; live listeners, other files, symlinks and other owners are preserved. This recovery does not restore sharing or worker authorization. An OAuth grant alone cannot read queued work. Keep secrets and pairing codes out of screenshots, exports and logs.

The public listener exposes only OAuth/discovery and three scoped MCP tools over its owner-only Unix socket. It never exposes the local `/api/` routes. OAuth uses PKCE and signed client assertions pinned to ChatGPT client metadata/keys, plus current official network ingress policy. Stored authorization tokens are hashed. The unrelated Infinite Canvas connector and tunnel remain separate.

## Request integrity and recovery

Nine operations are supported: generate, tutor, group, complete, assess, reconcile-roadmap, review-environment, materialize-work and materialize-outcome. The retrospective-group capability uses group with mode catch-up when the player opens group chat. It summarizes recorded public work once per captured interval; it never starts a continuous conversation or silently sends private tutoring. Requests bind stable IDs to exact operation/payload hashes. Prioritized interactive work cannot indefinitely starve older assessments. Worker claims bind answers to their original task; duplicate identical answers are idempotent and changed duplicates are rejected. Large Unicode packets are chunked without dropping curriculum or evidence; all parts must be read before submission. The game separately validates curriculum scope, dialogue grounding, contribution eligibility and academic evidence. A completion answer cannot itself award individual mastery.

Generation, private tutor and captured completion requests preserve their exact payload through reload. Retry the saved request explicitly. A client-rejected reply can be reopened in Settings for correction: the original request/hash stays fixed and the previous answer stays in private audit history. Recover worker releases stale claims without rerolling questions. Disconnected terminals show a connection notice and a Reconnect ChatGPT button that opens the existing sharing controls; it does not enable sharing or send work. Use Retry answer check after a completion interruption: it keeps the original provider, request ID, question, captured submission and evidence cutoff. Later unsent edits remain available while it waits; acceptance freezes the captured revision. Automatic completion assessment uses that accepted cutoff and does not queue a second assessment for later unsent work. Group replies also retain their exact provider, question, selected speakers and public snapshot across reload. Use Retry saved group question explicitly. Duplicate clicks coalesce, and a delivered reply cannot append twice. A newer group question supersedes older replies while retaining their captured context. Workspace changes refuse stale replies; ask a new question for the current revision. A chosen speaker who leaves or encounters danger defers delivery until available again. Private tutor context remains excluded. This does not make every optional native operation resumable.

Queue limits bound outstanding transport work and storage, not gameplay tutoring count or a hint fee/cooldown. The simulation continues while the external ChatGPT worker thinks or waits. No guaranteed response latency is claimed. Optional native capabilities (autonomous work and materialization) are not advertised by this handoff.

## Execution field integrity

Assessment findings use exactly `execution: "not-run" | "executed"`. This records whether matching code actually ran; it does not encode test success, solution correctness or mastery. `passed`, `failed`, booleans, objects and null are invalid execution states. The handoff queue rejects these shapes while retaining the claim for correction; the learner independently rejects them atomically before allocating evidence or visits. An `executed` finding still needs the captured matching runtime receipt and human artifact references. Existing historical packets are retained without silently rewriting their raw content.

## Terminal submission and conversation

Solo terminals use a single private Terminal AI conversation, with no separate answer box or submission button. Every outgoing tutor prompt begins with `@study`; `studyPrompt` and bridge instructions also retain that prefix. Each request captures the exact question, all private messages, saved work/revision, recent submissions, actual finished execution evidence, contract and relevant curriculum/progress context. Requests use `mode: "terminal-dialogue"` and require `{text:string, complete:boolean}`. Incomplete reasoning gets a focused follow-up; a correct, sufficiently supported accumulated answer gets explicit completion. The tutor’s own explanations are assistance, not learner work. Native ChatGPT Study Mode remains unverified.

An accepted `complete:true` reply captures the human messages and saved work, then uses the existing once-only reward and separate mastery-assessment path. No second completion request is needed. Malformed decisions, lost connections, changed questions and stale replies cannot award access. One pending turn runs per private conversation; failures preserve exact-context retry across reload, and a new turn supersedes an interrupted older check. Previously saved work is retained in a collapsed section. Legacy shared saves retain their public group conversation, editor and frozen `complete` operation; private context stays excluded from public requests.

The persistent relay retains queued requests and sessions across game-server restarts. It does not run a model or wake an ended ChatGPT chat automatically. Released terminal turns are served either by the embedded live terminal app in a regular ChatGPT chat (see the section below; this is the current path) or by a legacy worker chat that polls `get_study_handoff`. These flows are tested with synthetic controlled transport and do not prove real model grading quality.

The conversational client validates its saved question, revision, workspace and authored turn before release and again before applying a reply. A dialogue reply missing an explicit boolean `complete` is interrupted rather than silently treated as an unsolved response. `tests/terminal-dialogue-harness.test.ts` verifies the real isolated HTTP relay/queue/worker path through correction, sharing revocation, worker release, save/reload, exact retry and once-only reward; the worker answers remain synthetic, so this establishes transport and state behavior rather than real model grading quality.

## Live terminal relay through the MCP App — verified 2026-10-18

`scripts/terminal-relay-app.mjs` moves the real solo terminal conversation (`mode: "terminal-dialogue"`) off the polling worker and onto the host-turn path, without changing the game client. The game still sends each learner message as a tutor request to the relay queue and polls `/api/bridge/result` for the answer, so saved requests, exact retry, correction (`reopen`), Recover worker, audit history and the once-only reward all keep their existing code paths. What changes is who serves the queued job: the embedded app in a regular ChatGPT conversation claims it instead of a polling worker chat.

Five OAuth-bound tools sit beside the three legacy worker tools and the four synthetic demo tools. `open_study_terminal` (model-facing) renders the same `public/terminal-mcp-app.html` in live mode under `ui://zombie-study/terminal-relay-v1.html` and creates one relay session per OAuth owner. `claim_study_terminal_turn` and `read_study_terminal` are app-only (`_meta.ui.visibility: ["app"]`). `reply_study_terminal_job` (model-facing) takes `{relayId, turnId, text, complete}`. `read_study_terminal_context` (model-facing) returns a curriculum or progress part that an oversized turn omitted. None of them accepts a worker-session code.

Flow: the app polls `claim_study_terminal_turn` every 2.5 s (bounded; it pauses after ten minutes with a Resume button). Claiming calls the queue's `get` with a selector that accepts only `tutor` jobs with `mode: "terminal-dialogue"` for the worker identity `app-<hash(owner)>`; generation, assessment, group and NPC jobs are never served to the app. A claimed job becomes a turn with a fresh random `turnId`; the queue's secret claim stays server-side and never enters the chat. The app posts the turn's `@study` prompt once through `ui/message`: it carries the exact question (title, prompt, rubric, starter), the game's `instruction`, `responseFormat`, learning contract, saved workspace and revision, recent submissions, finished execution evidence, any correction note, and the captured conversation. The prompt is bounded (`PROMPT_LIMIT` 40,000 characters): progress context and then curriculum text are omitted first, with an `omitted` list telling the model to fetch them through `read_study_terminal_context`; the newest messages are kept if the conversation alone is still too large (the full packet remains in the queue job). The host starts a model turn; the model calls `reply_study_terminal_job`, which submits `{text, complete}` to the same queue job through `queue.submit`, so the queue's terminal-dialogue validation (`complete:boolean`, bounded text) applies and the game client applies the reply exactly as before: `complete:true` captures the human messages and saved work and uses the existing once-only reward and separate mastery path, and never a second reward. The app then shows the reply and returns to waiting.

Protections: a relay session is OAuth-owner isolated and bounded (64 sessions, idle eviction after an hour without a pending turn); claims check the app's revision; replies are idempotent per `turnId` (an identical duplicate returns the same state, a different reply for a finished turn is rejected, a reply for a superseded turn is rejected); a `reopen` correction or a requeued claim yields a new `turnId`, so stale replies cannot land. Nothing is claimable until live study requests are released in game Settings (`queue.enable`); opening the app releases nothing. Stop worker & sharing, Disconnect/revoke, OAuth disconnection and relay shutdown requeue every app claim through `releaseWorker`, and a reply after sharing is disabled is refused by the queue. After a relay restart the in-memory session is gone but the queue's working job for the same owner is recovered as a fresh turn on the next claim. The legacy worker tools are unchanged and still require the worker-session code; a legacy worker chat, if one is active, may still pick up terminal jobs (whichever claims first). The relay's `/api/handoff/status` reports `public.terminalRelay` session and pending-turn counts only, and the game's queued-turn status now mentions the terminal app.

Coverage: `tests/terminal-relay-app.test.mjs` (tools, gating, selector, prompt contents, idempotency, correction, release, restart recovery, owner isolation, bounds, context read, chunked packets), `tests/chatgpt-public-bridge.test.ts` (the OAuth HTTP path, stop-worker requeue and resumed claims), `tests/terminal-relay-harness.test.ts` (the real game client through the real relay routes with the app as the server-side worker: follow-up, interruption without a late reward, save/reload, exact retry, exactly one key, no mastery) and `tests/browser/terminal-mcp-app.spec.ts` (fake host: one `@study` post per released game message, reply rendering, no demo or legacy tool calls). These prove transport and state with synthetic replies, not grading quality.

Live verification in the real ChatGPT web client on 2026-10-18, after `npm run bridge:stop`/`bridge:start`, tunnel start and **Refresh tools**: a fresh chat called `open_study_terminal` once and the live app rendered waiting; `LIVE_STUDY_BRIDGE=1 npx playwright test tests/browser/live-dialogue.spec.ts` then sent two synthetic terminal turns from an isolated game page. Each turn was claimed and posted by the app, started a real model turn, and was answered through `reply_study_terminal_job` (first `complete:false`, then `complete:true`); the game applied exactly one key and both requests ended applied, with no legacy worker session and no `get_study_handoff` call.
