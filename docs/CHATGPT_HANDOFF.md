# ChatGPT handoff connector

This is a separate non-API ChatGPT connector for the game, adapted from generic transport/security code in the user's Infinite Canvas project. It does not verify or claim native ChatGPT Study Mode. The original native adapter remains available separately. No production credentials, job state or application generator were copied from the reference project; see `scripts/chatgpt-security/PROVENANCE.json`.

## AI-authored new runs

`design-run` uses the same ChatGPT handoff for fictional world authoring. It is separate from study generation. Requests contain a versioned identity, run seed, bounded prior fictional summaries, and an optional rejected candidate with validation errors. Version 3's content phase also supplies the accepted structural proposal and its exact fictional object inventory. The shared `src/run-design-contract.mjs` parser rejects additional request fields; learner state, curriculum, saved conversations and credentials are not part of these packets.

Fresh packets use request `version: 3`, `designVersion: 3`, and captured stages for concepts, selection, structure, structure review, room content planning, focused object batches, content review and targeted revision. The shared quality contract describes each stage's exact input and reply. The client validates actual geometry before freezing its inventory; batches and revisions cannot change structure, bindings or unrelated entries. Retained request `version: 2` keeps its original `structure` and `content` phases. Requests remain bounded to 1.5 MB, structural proposals to 100 KB and assembled content to 512 KB. The combined accepted design is assembled locally and limited to 900 KB. Native chunk reading remains mandatory when the complete prompt, including its instructions and metadata, exceeds the inline limit. See [AI-authored runs](AI_RUN_DESIGNS.md) for review/stopping behavior and [environmental authoring](ENVIRONMENT_AUTHORING.md) for object, drawing and repetition constraints.

Retained request version 1 packets keep their original contracts: absent `designVersion` requires design version 1; `designVersion: 2` requires the individual room/furniture/prop scenes introduced in version 2. Their previous byte limits remain unchanged. A reconnect never silently upgrades a captured request. All versions accept structured data, never generated code or arbitrary asset loaders.

Each generation has its own chat code and native scope (`runId` equals the generation ID, `encounterId` is `run-design`). The player's pasted request uses `get_current_study_question` to retrieve a `prepare` turn whose operation is `design-run`; `finish_study_preparation` returns the exact correlated phase JSON. The turn contains world-design instructions rather than tutoring instructions. Its bound continuation waits up to five seconds for the next phase or repair of this same generation and chat; if none arrives it returns waiting and the assistant stops. It cannot continue into a study question, assessment or another run's design. Native preparation routing keeps it out of legacy worker claims. The game validates geometry, novelty and complete object content before adopting the result; a delivery receipt alone does not mean a design was accepted.

Transport retries preserve the exact request ID, payload and provider. A geometry repair is a new request within the same generation, carrying the previous candidate and its validation errors. Explicit cancellation discards only the matching design receipt and prevents late completion; ordinary timeouts and relay outages retain the queued request for retry. Saved runs keep their adopted designs and never request a replacement during reload. No API key or new provider is used. A bridge running older code must be restarted through its normal service controls before it advertises this operation; restarting the bridge does not restore sharing or a worker session.

Offline transport tests use synthetic designs and an isolated queue/server. They verify schema rejection, exact identity, cancellation, durable retry and native delivery; they do not establish external model design quality or release real player data.

## Current native conversation flow

In the learning workspace, the main session button changes from **Start next question** to **Stop question**, then **Resume in new chat**. Stopping saves the issued question and stops accepting its old chat's result, including across reloads. Resuming preserves the exact question and curriculum binding but creates a fresh request and chat code; copy the request into a new ChatGPT chat. Earlier messages remain in the original ChatGPT chat and are not transferred or treated as learner evidence in the new session.

Copy the request from the game into a fresh ChatGPT chat for each terminal opening. The request includes a terminal chat code; pass it as `chat` on every `get_current_study_question` call. If ChatGPT's tool has no `chat` input, refresh it through Plugins → zombie-escape-study-game → Manage → Refresh tools, then use a fresh chat. A `chat_required` response means the code was omitted while scoped work is waiting; it does not mean the game has no question. The relay leaves that work unclaimed and never exposes another terminal's code. Historical unscoped requests retain their existing behavior.

Reloading the same game tab preserves its terminal chat code in session storage; an explicit terminal opening still rotates it. Once ChatGPT picks up the question, the game shows that completion is pending. If ChatGPT finishes but its completion call fails, use **Copy completion retry** and paste it into that terminal's existing chat, preserving the actual conversation and exact question binding. Clipboard failures reveal selectable request text. The public bridge's bounded local diagnostics classify known tool calls and returned/rejected results without retaining arguments, answers, codes or credentials. These server diagnostics take effect on the next normal bridge restart; restarting also disables sharing until released again.

New question packets request at most one identical completion retry for an explicit retryable response, temporary connection error or timeout. Identical accepted retries return the original receipt without applying twice. Permission/safety denials, authentication errors, disconnected chats and stale questions stop for recovery. A busy bridge returns an explicit retryable tool error with reason `bridge_busy`; diagnostics record it and distinguish a sent receipt (including duplicates) from ordinary returned tool output. These instructions cannot guarantee that ChatGPT retries an upstream failure, and a missing server call does not establish its cause. The existing same-chat completion retry remains the manual fallback.

Keep the game and a regular ChatGPT conversation in separate tabs. Press E at a game station, then ask the connected ChatGPT chat to get the current game study question. The model-visible `get_current_study_question` tool returns one released native phase as ordinary tool output: `prepare` for question generation, `question` for the learner conversation, or `assess` for the separate final learning review. It needs no worker-session code, polling worker or UI card. If nothing is waiting it says so once and ends the call. The optional `open_study_terminal` live card can automatically announce questions; it has no alternative answer composer.

For `prepare` and `assess`, ChatGPT reads the exact frozen payload and returns its operation-specific JSON through `finish_study_preparation({relayId, turnId, jobFingerprint, response})`, where `response` is the complete JSON object encoded as a string. Larger packets carry a `payloadManifest` and required `payload` reads through `read_study_terminal_context({relayId, turnId, part:"payload", index})`. Every index must be read before submission. Chunks preserve the full original curriculum, source criteria, policies, progress rows, authored history, assistance IDs and chronology; no oversized evidence is silently dropped. The queue's existing operation validation and the game's independent problem/assessment validation still apply. A preparation callback cannot finish a learner question, and the legacy reply tool cannot finish either native phase.

Generation and question-completion receipts can include a bound `completion.continuation.after` token. ChatGPT calls `get_current_study_question({after})` once with that token; the server waits at most five seconds for the browser to apply the result and queue the same question's next phase. Generation may continue to the actual question station in its shared room, while question completion can continue only to an assessment for the exact same run and encounter. Owner, claim and frozen-request fingerprint remain bound. A waiting result ends the chain, without repeated tool polling or unrelated-job selection. Development practice needs no formal assessment. Final assessment has no next phase.

All intermediate questions and answers use ChatGPT's native conversation. At the end, ChatGPT calls `finish_study_question` with the exact relay ID, turn ID, question fingerprint, outcome, final text, named facet observations and attributed native transcript. The server adds `complete:true`; callers do not supply it. A solved result must establish every original base facet, and a gap must name an explicitly acknowledged facet. Unasked facets remain unknown. Identical callback retries are harmless; conflicting, wrong-mode or stale completions are rejected. A tool receipt means the bridge accepted a result for delivery, not that the browser awarded a key or academic mastery. The game independently validates its frozen question, run, provider, workspace and revision before applying one completion, then assesses learning separately.

Only transcript entries attributed to the user become learner artifacts. Assistant explanations remain assistance, and host-model transcription is labeled as such rather than live game input. Transcript bounds are 100 entries, 8000 characters per entry and 100000 characters total. The request retains any unsent legacy draft as non-evidence and preserves the original saved conversation. Formal assessment retains source criteria and assistance provenance; a native finish or key never directly grants curriculum credit.

A pending question or generation request survives reload and human death. Finishing after death/extraction records learning but grants no key/access. The normal game interface stays visible as a live spectator view. Native sessions can remain pending for up to eight hours while the requester stays live; legacy turns retain their thirty-minute limit. Exactly the saved request is retried after interruption. Changing the curriculum focus preserves an already issued question; new scheduling uses the selected focus. Native scope metadata travels outside the frozen payload and hash, binds once on an exact retry, and rejects later changes. Legacy workers cannot consume scoped native generation/assessment or direct questions; unscoped historical work remains compatible. An untouched restored legacy generation/assessment claim can migrate when the same saved request first binds its native scope, while current active legacy and stable native claims stay intact.

No OpenAI API key is used. Intermediate answers have no game-relay delivery round trip. Initial generation/claim, native model response, final completion, assessment and browser application remain distinct stages. Queue diagnostics expose metadata timestamps (`createdAt`, `firstPolledAt`, `claimedAt`, `completedAt`, `resultReadAt`), while the client records creation, response receipt and application; status/export omits native private transcript content.

The public connector exposes fifteen tools: three legacy worker tools, four synthetic demo tools and eight live relay tools. After restarting the bridge for new server code, refresh/rescan the ChatGPT connector's tool definitions so `get_current_study_question`, `finish_study_preparation`, `read_study_terminal_context` and `finish_study_question` are discoverable. Existing OAuth authorization remains scoped to this game; release of study requests is separate and starts disabled on a bridge restart. Every outgoing tutor prompt begins with `@study`; `studyPrompt` and bridge instructions also retain that prefix. Each request captures the exact question, all private messages, saved work/revision, recent submissions, actual finished execution evidence, contract and relevant curriculum/progress context. Native ChatGPT Study Mode remains unverified.

A granted key is announced where the player is looking, not only as a changed HUD number: a small "Key granted" pill over the world that fades after about two seconds, one pulse on the HUD key count, a "Key granted" line in the open conversation panel (cleared on Leave terminal), and a latch sound cue with the caption "[Lock releases · key granted]" for the player's own terminal only. Context per turn is bounded, not cumulative without limit: the game sends the whole private conversation of that one terminal plus the curriculum and progress text (about 70 kB and 100 kB) to the local relay with every message, but the posted ChatGPT turn carries at most `PROMPT_LIMIT` (40,000 characters): progress context and curriculum are omitted first and fetched on demand through `read_study_terminal_context`, then the oldest messages, keeping the newest (at most 80). A real track's turn is about 9–10 k characters. Each turn is self-contained, so ChatGPT losing older chat context never breaks a reply.

### Knowledge probing stance

The terminal assumes the learner already knows the material; the learner says when they do not. The instruction tells the tutor not to walk the rubric item by item but to open with the highest-leverage question, the one whose correct answer necessarily depends on the other facets, so one good answer establishes several (`implied`, with `impliedBy` naming the demonstrated facet). How an answer is given is evidence too: precise vocabulary, correct step order and unprompted boundaries count for knowledge, while hedging, guessed numbers or asking what the question means are signals to probe one level down rather than to assume a gap. When the learner declares they do not know a facet or asks for the answer, the tutor does not lecture or withhold the key. If that facet encompasses others (the apex X whose answer depends on Y and Z), the tutor probes Y and Z next, one level down, so the recorded gap is only the parts actually missing; a facet with nothing below it is named as a `gap` with the learner's words. When the question never listed those parts, the tutor declares each as a new facet with `partOf` naming the known facet and a short `description`; the game accepts such a declaration only for a known parent, at most two levels below the question's own facets and at most sixteen per reply, adds it to the encounter's facet universe, and records it like any other facet, so a gap can read "enumerative combinatorics (part of integer partition identities)" while generating functions is established. If the parts all turn out to be known the tutor returns to the apex and asks it again: known parts never imply the apex, since the apex is also combining them, so it is established only when answered. Once every remaining facet is established or declared at its lowest level the tutor returns `complete:true` with `outcome:"gap"`.

The game validates the report (`parseProbeReply`): a malformed `outcome` or `knowledge` interrupts the reply like a missing `complete`, ids outside the question's facets are dropped, and `complete` stays the only key decision. Every validated turn is kept on the encounter (`e.probe`), where later turns re-judge earlier facets, and the terminal HUD shows how many facets are established. A conceded completion records each declared facet, or every unestablished facet when none were named, once per encounter in `study.knowledgeGaps` with the learner's statement, track, objectives and depth. That record survives save/reload and rides the carried study state into the next run, appears in the curriculum inspector, and is appended to the next tutor request's `progressContext` on the same track so the next question can target it. It is a study target, never a failure, mastery or a learner ledger change; the separate assessment path still judges independence.

Established facets are carried the same way. After every validated turn the encounter's `demonstrated` and `implied` facets (with `impliedBy`) are mirrored into `study.knowledgeEstablished`, one record per encounter facet, replaced or withdrawn when a later turn re-judges that facet. The next tutor request on the same track lists them in `progressContext` as already known, with the instruction not to re-probe them unless the current answer contradicts one, so a correct answer to X records X and every Y and Z it implied, and later terminals do not ask about them again. The inspector shows them beside the gaps; they are terminal observations, not curriculum credit.

A gap closes when the same facet is later established at another terminal on that track, matched by stable facet id or by identical facet text when a question uses its own rubric ids. The record keeps its original statement and gains `resolved` (when, where, demonstrated or implied). The next tutor request lists open gaps to ask about directly and closed gaps as "since established, so the facet it blocked can be asked again"; the inspector shows open and closed counts. Which scope the next terminal gets is still the curriculum scheduler's choice, but the live generator now sees the records: every `generate` request carries `probeRecords` (`probeRecordsForTrack`: the last 40 established facets, 20 open gaps with the learner's statement and 20 closed gaps for the track, each with its parent when it was a declared part) and its `generationPolicy` and worker contract say to build the question around open gaps inside the eligible scope with the blocked facet as the apex. Only a gap marked `reuseInScopeDefinitions` (one of a question's own facets, recorded on exactly the scope the contract registers, whose definition is unregistered or already holds that facet unchanged) may add its id to `scopeDefinitions`, so a recorded gap can never ask the generator to rewrite a stable scope definition; the policy also says to avoid spending the question on established facets, and to re-ask what a closed gap blocked. The contract is still copied exactly and validated locally. Development practice appends one line of open gap descriptions for the track to its rehearsal prompt.

An accepted `complete:true` reply captures the human messages and saved work, then uses the existing once-only reward and separate mastery-assessment path. No second completion request is needed. Malformed decisions, lost connections, changed questions and stale replies cannot award access. One pending turn runs per private conversation; failures preserve exact-context retry across reload, and a new turn supersedes an interrupted older check. Previously saved work is retained in a collapsed section. Legacy shared saves retain their public group conversation, editor and frozen `complete` operation; private context stays excluded from public requests.

The persistent relay retains queued requests and sessions across game-server restarts. It does not run a model or wake an ended ChatGPT chat automatically. Released terminal turns are served either by the embedded live terminal app in a regular ChatGPT chat (see the section below; this is the current path) or by a legacy worker chat that polls `get_study_handoff`. These flows are tested with synthetic controlled transport and do not prove real model grading quality.

The conversational client validates its saved question, revision, workspace and authored turn before release and again before applying a reply. A dialogue reply missing an explicit boolean `complete` is interrupted rather than silently treated as an unsolved response. `tests/terminal-dialogue-harness.test.ts` verifies the real isolated HTTP relay/queue/worker path through correction, sharing revocation, worker release, save/reload, exact retry and once-only reward; the worker answers remain synthetic, so this establishes transport and state behavior rather than real model grading quality.

State is OAuth-owner isolated, revision and turn checked, idempotent per turn, bounded to 80 messages and 64 sessions, and awards at most one synthetic demo key. These tools never touch the legacy queue, worker session or sharing flag; opening the demo does not release real requests.

Each Send in the embedded UI stages the learner message, then posts the returned `@study` prompt (question, rubric and full captured history) to the host through `ui/message`. The host starts a fresh ChatGPT turn; the model answers by calling `reply_study_terminal_turn`, and the UI refreshes with bounded reads until the pending turn clears. No coding chat polls `get_study_handoff`.

## Legacy per-turn terminal relay through the MCP App — verified 2026-10-18

`scripts/terminal-relay-app.mjs` moves the real solo terminal conversation (`mode: "terminal-dialogue"`) off the polling worker and onto the host-turn path, without changing the game client. The game still sends each learner message as a tutor request to the relay queue and polls `/api/bridge/result` for the answer, so saved requests, exact retry, correction (`reopen`), Recover worker, audit history and the once-only reward all keep their existing code paths. What changes is who serves the queued job: the embedded app in a regular ChatGPT conversation claims it instead of a polling worker chat.

Five OAuth-bound tools sit beside the three legacy worker tools and the four synthetic demo tools. `open_study_terminal` (model-facing) renders the same `public/terminal-mcp-app.html` in live mode under `ui://zombie-study/terminal-relay-v1.html` and creates one relay session per OAuth owner. `claim_study_terminal_turn` and `read_study_terminal` are app-only (`_meta.ui.visibility: ["app"]`). `reply_study_terminal_job` (model-facing) takes `{relayId, turnId, text, complete}`. `read_study_terminal_context` (model-facing) returns a curriculum or progress part that an oversized turn omitted. None of them accepts a worker-session code.

Flow: the app polls `claim_study_terminal_turn` every 2.5 s while the panel is open, backing off to every 10 s after ten minutes without a game message (a game message, window focus or the Resume button restores the quick cadence); it never stops listening on its own. The relay reports `public.terminalRelay.activeSessions`, counting only app sessions that called in within the last 20 s; the game treats a relay with no active session and no worker as "nothing is listening". In that state, or when the bridge is offline, the chat panel shows one **Connect ChatGPT** button. It starts the public connector if needed, releases live study requests, then opens a new, empty ChatGPT chat (`https://chatgpt.com/`) and copies the study-terminal request to the clipboard, and clears its notice once a terminal app calls in. The tab is reserved during the click, because browsers block tabs opened later, and is closed if setup fails or something is already listening. It is opened under a fixed window name (`zombie-study-chatgpt`) with its opener kept, so a later press gets the same tab back and moves it to a new chat instead of adding a tab the player has to close; an empty-URL `window.open` on that name returns the existing tab without navigating it, and because the opener is kept the name survives ChatGPT's cross-site navigation and even a reload of the game page. A new tab is created only when none exists; a reused tab is never closed by the game. The fallback Open ChatGPT link targets the same name. The request is not put in the URL because ChatGPT sends a `?q=` request at once, before the player can choose the model and thinking level; the notice tells the player to choose those, paste and press Enter (or shows the request text if the clipboard write failed). It is copied at the start of the click, while the game still has focus and user activation. The terminal also shows the exact request in a read-only text box with a Copy prompt button and explicit clipboard success/failure feedback, so it remains available even if automatic copying fails. The fallback Open ChatGPT link retries the copy. These controls clear when a terminal starts listening. If the browser blocks the tab, an Open ChatGPT link with the same chat appears instead. Claiming calls the queue's `get` with a selector that accepts only `tutor` jobs with `mode: "terminal-dialogue"` for the worker identity `app-<hash(owner)>`; generation, assessment, group and NPC jobs are never served to the app. A claimed job becomes a turn with a fresh random `turnId`; the queue's secret claim stays server-side and never enters the chat. The app posts the turn's `@study` prompt once through `ui/message`: it carries the exact question (title, prompt, rubric, starter), the game's `instruction`, `responseFormat`, learning contract, saved workspace and revision, recent submissions, finished execution evidence, any correction note, and the captured conversation. The prompt is bounded (`PROMPT_LIMIT` 40,000 characters): progress context and then curriculum text are omitted first, with an `omitted` list telling the model to fetch them through `read_study_terminal_context`; the newest messages are kept if the conversation alone is still too large (the full packet remains in the queue job). The host starts a model turn; the model calls `reply_study_terminal_job`, which submits `{text, complete, outcome?, knowledge?}` to the same queue job through `queue.submit`, so the queue's terminal-dialogue validation (`complete:boolean`, bounded text, `outcome` solved|gap, well-formed `knowledge`) applies and the game client applies the reply exactly as before: `complete:true` captures the human messages and saved work and uses the existing once-only reward and separate mastery path, and never a second reward. The app then shows the reply and returns to waiting.

Protections: a relay session is OAuth-owner isolated and bounded (64 sessions, idle eviction after an hour without a pending turn); claims check the app's revision; replies are idempotent per `turnId` (an identical duplicate returns the same state, a different reply for a finished turn is rejected, a reply for a superseded turn is rejected); a `reopen` correction or a requeued claim yields a new `turnId`, so stale replies cannot land. Nothing is claimable until live study requests are released in game Settings (`queue.enable`); opening the app releases nothing. Stop worker & sharing, Disconnect/revoke, OAuth disconnection and relay shutdown requeue every app claim through `releaseWorker`, and a reply after sharing is disabled is refused by the queue. After a relay restart the in-memory session is gone but the queue's working job for the same owner is recovered as a fresh turn on the next claim. The legacy worker tools are unchanged and still require the worker-session code; a legacy worker chat, if one is active, may still pick up terminal jobs (whichever claims first). The relay's `/api/handoff/status` reports `public.terminalRelay` session and pending-turn counts only, and the game's queued-turn status now mentions the terminal app.

Coverage: `tests/terminal-relay-app.test.mjs` (tools, gating, selector, prompt contents, idempotency, correction, release, restart recovery, owner isolation, bounds, context read, chunked packets), `tests/chatgpt-public-bridge.test.ts` (the OAuth HTTP path, stop-worker requeue and resumed claims), `tests/terminal-relay-harness.test.ts` (the real game client through the real relay routes with the app as the server-side worker: follow-up, interruption without a late reward, save/reload, exact retry, exactly one key, no mastery) and `tests/browser/terminal-mcp-app.spec.ts` (fake host: one `@study` post per released game message, reply rendering, no demo or legacy tool calls). These prove transport and state with synthetic replies, not grading quality.

Live verification in the real ChatGPT web client on 2026-10-18, after `npm run bridge:stop`/`bridge:start`, tunnel start and **Refresh tools**: a fresh chat called `open_study_terminal` once and the live app rendered waiting; `LIVE_STUDY_BRIDGE=1 npx playwright test tests/browser/live-dialogue.spec.ts` then sent two synthetic terminal turns from an isolated game page. Each turn was claimed and posted by the app, started a real model turn, and was answered through `reply_study_terminal_job` (first `complete:false`, then `complete:true`); the game applied exactly one key and both requests ended applied, with no legacy worker session and no `get_study_handoff` call. Sharing was released only for the run and disabled afterwards. Evidence: `docs/evidence/chatgpt-terminal-relay-live.json`, `chatgpt-terminal-relay-live-followup.jpg`, `chatgpt-terminal-relay-live-complete.jpg`, `chatgpt-terminal-relay-live-game.png` and `chatgpt-terminal-relay-live-spec.log`. The live spec now accepts either an open terminal app or a legacy worker and logs which served.

## Tool approval cards and the "Suspicious Instruction" stall — fixed 2026-10-19

A real game turn on 2026-10-19 stayed at "Picked up by ChatGPT; waiting for its reply" indefinitely. The relay had claimed and posted the turn and the model did call `reply_study_terminal_job`, but ChatGPT parked that call behind an **"Allow ChatGPT to use zombie-escape-study-game?"** card marked **Suspicious Instruction** ("tool description prescribes how to classify learner evidence, completion, probing, and output behavior"), and the card sat in the chat column behind the app panel in full view, so nobody answered it. ChatGPT screens connector tool _documentation_ for behavioral directives; the reply tool's description carried the whole probe policy. Model-facing descriptions (`open_study_terminal`, `read_study_terminal_context`, `reply_study_terminal_job`) now say only what each tool does and takes, and the complete tutoring policy travels in every posted turn as `TURN_INSTRUCTION` (the host user message the model already follows); `tests/terminal-relay-app.test.mjs` fails if a directive creeps back into a description or drops out of the turn. The relay must be restarted and the connector's tools refreshed in ChatGPT (**Settings → Plugins → zombie-escape-study-game → Manage → Refresh tools**, then a fresh chat) for ChatGPT to see the new descriptions.

Even without the flag, ChatGPT asks once before a connector's write tool runs; choose **Always allow** on that first card so later replies land without a click. While a reply is outstanding, both the embedded app (after about twelve seconds) and the game's terminal status (after fifteen seconds in the "working" phase, tracked by `transportPhaseAt`) now say where that card is and what to press. The queue also expires queued requests that nobody served within a day, like answered ones: a reloaded or abandoned run used to leave its 180 kB terminal turn queued forever, and 128 such turns would have filled the transport; retrying the exact saved request simply re-creates it. The relay's requester-live window (`REQUESTER_LIVE_MS`) is 75 s rather than 30 s: Chrome throttles a game tab that has been hidden for five minutes (the player is over in the ChatGPT tab) to one timer wake a minute, and a 30 s window treated that game as gone and released its claim.

Limitations: only the synthetic live-spec question was exercised, so the size-omission path and `read_study_terminal_context` have unit coverage but no live observation; a real curriculum track (70–130k characters of curriculum and progress text) will always take that path (the 2026-10-19 turn did omit both parts, 9.4k-character prompt, before stalling on the approval card above). The `ui/message` prompt still does not appear as a user bubble, and ChatGPT turned the first `@study` composer text into its Study-mode chip; neither establishes native Study Mode. The app must stay open in the chat's side panel while the player works, and it pauses after ten minutes without a game message. An OAuth grant plus released sharing is sufficient for this path; the worker-session code is a legacy-tool protection only. Real model grading quality remains uncertified.
